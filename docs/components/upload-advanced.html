Upload — Advanced

Chunked transport, resumable uploads that survive a reload, clipboard & folder ingestion, custom transports, tus 1.0 mode and the headless Orion.upload() controller. See Upload for the everyday features and the full props/events/methods reference.

The mock transport

Every demo on this page runs fully offline against Orion.upload.mock({ latency, failRate, speed, tick, seed }) — an in-memory server emulator built for testing and prototyping. It returns a function that plays back realistic progress events for whole-file uploads, and it also exposes .request, a second emulator that understands chunked (Content-Range / X-File-Id) and tus 1.0 (Tus-Resumable) protocols, so you can develop and test resumable flows without a backend. .server is a Map of what each virtual upload has received so far, and .log records every attempt (handy to prove retries / resumed chunks actually happened).

      const mock = Orion.upload.mock({ latency: 250, failRate: 0.1, speed: 1_500_000, seed: 7 });
      el.uploader = mock;              // whole-file or chunked uploads call mock(file, {onProgress, signal, chunk})
      el.url = '/upload';              // required so the element knows a transport exists
      // — or, for the URL + Content-Range / tus code paths —
      el.request = mock.request;       // replaces only the HTTP primitive; chunk/tus framing stays real

Chunked upload

Set chunk-size and files larger than it are split into parts sent with up to chunk-parallel concurrent requests, each retried independently with exponential backoff. The default framing sends Content-Range, X-File-Id, X-File-Name, X-Chunk-Index and X-Chunk-Count headers with an octet-stream body — override any of it with chunk-request(chunk, base), and post-process the assembled file server-side with finalize(ctx).

Drop a file larger than 256 KB above and watch the log: several chunks are in flight together, and a simulated failure only retries that chunk, not the whole file.

Resumable upload

With resumable, each file gets a stable fingerprint (name + size + last-modified + a SHA-256 of its first/last 64 KB, via SubtleCrypto) and the set of completed chunk indexes is persisted to IndexedDB (falling back to localStorage, or Orion.idb from the services package when present). Re-adding the same file — after a reload, a crashed tab, or a lost connection — only sends what's missing. The element also auto-pauses on offline and resumes on online.

Add a file, let it get partway, then click Simulate reload: a fresh <o-upload> is created (as a real page reload would give you) and the same File is re-added — the log shows o-resumed firing with a non-zero offset instead of the upload starting over.

Progress, speed & ETA

Per-file o-progress events carry a smoothed speed (bytes/s) and eta (seconds); the built-in list row and summary bar already render both. Slow the mock transport down to see them settle.

Clipboard paste

Focus (or hover, with paste="element", the default) the zone below and paste — a screenshot copied from the OS gets a generated, timestamped filename. Set paste="window" to accept a paste anywhere on the page while this element is connected.

Folder upload

Set directory for a native folder picker (Chromium/WebKit), or just drag a folder onto any zone — both paths walk the tree with webkitGetAsEntry/FileSystemDirectoryReader and keep each file's relative path (shown as its name, and sent to the server as its relativePath).

Custom transports

The uploader hook fully replaces the transport — receive the File (or, mid-chunk, a { index, start, end, blob, fileId, total } chunk descriptor) and resolve with whatever the server returned. This example uses fetch with an AbortController instead of the built-in XMLHttpRequest transport (wrapped here to still simulate progress, since fetch has no native upload-progress event):

      el.uploader = async (file, { onProgress, signal, item }) => {
        const body = new FormData();
        body.append('file', file, file.name);
        const res = await fetch('/upload', { method: 'POST', body, signal });
        if (!res.ok) throw new Error('Upload failed: ' + res.status);
        onProgress(file.size, file.size);
        return res.json();               // becomes item.response / o-success detail.response
      };

For finer control keep the built-in multipart/chunk/tus framing and swap only the HTTP call with request — this is exactly what Orion.upload.mock().request plugs into for the demos on this page:

      el.request = ({ method, url, headers, body, onProgress, signal }) =>
        Orion.upload.request({ method, url, headers, body, onProgress, signal, withCredentials: true });

tus 1.0 mode

Set protocol="tus" to speak the tus resumable upload protocol: a POST creates the upload and returns a Location, then PATCH requests stream chunk-size-sized pieces with Upload-Offset; a HEAD re-checks the offset to resume after a drop. resumable also persists the returned URL so a reload can HEAD it directly instead of creating a new upload.

Programmatic API — Orion.upload()

For a fully headless flow (no custom element, e.g. from an existing <input type="file"> or a drop zone you already built), Orion.upload(files, options) → controller runs the exact same validation/queue/transport engine and returns a small controller: add, upload, pause, resume, cancel, retry, remove, clear, event subscription (on/off/once, or onAdd/onProgress/… callback options), a live files/stats getter and a done promise that resolves once the whole batch settles.

Server-side notes

The client makes no assumptions beyond the request shape it sends — any backend that accepts multipart FormData, raw Content-Range chunks or the tus protocol works. A minimal Node/Express handler for the default (non-chunked) multipart mode:

      import express from 'express';
      import multer from 'multer';

      const upload = multer({ dest: 'uploads/', limits: { fileSize: 25 * 1024 * 1024 } });
      const app = express();

      // matches the default field-name="file"; el.data adds extra form fields alongside it
      app.post('/upload', upload.single('file'), (req, res) => {
        res.json({ id: req.file.filename, name: req.file.originalname, size: req.file.size });
      });

A chunked endpoint reads the headers the default chunk-request framing sends and appends each chunk to a per-file temp path, keyed by X-File-Id:

      import fs from 'node:fs';

      app.post('/upload', express.raw({ type: '*/*', limit: '20mb' }), (req, res) => {
        const range = /bytes (\d+)-(\d+)\/(\d+)/.exec(req.header('content-range'));
        if (!range) return res.status(400).end();
        const [, start, , total] = range.map(Number);
        const fileId = req.header('x-file-id');
        const tmp = `uploads/${fileId}.part`;
        const fd = fs.openSync(tmp, fs.existsSync(tmp) ? 'r+' : 'w');
        fs.writeSync(fd, req.body, 0, req.body.length, start);
        fs.closeSync(fd);
        const done = fs.statSync(tmp).size >= total;
        res.json(done ? { id: fileId, name: decodeURIComponent(req.header('x-file-name')), size: total } : { ok: true, received: fs.statSync(tmp).size });
      });

For tus mode, point url at a real tus-node-server (or any conformant tus 1.0 server) — the client already speaks the protocol's creation, HEAD and PATCH steps. In every mode, keep max-size/accept client-side checks in sync with server-side limits: the client-side checks are a UX convenience, not a security boundary — always re-validate size, type and content on the server.
